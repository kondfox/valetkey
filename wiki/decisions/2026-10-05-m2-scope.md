# M2 ships in two PRs, with TLS moved to M3 and protected targets unfenced until M4

Date: 2026-10-05 · Status: Active

## Context
M2 (the Postgres read path) covers secret sources, a process runner, the Postgres driver and the
first data tools. The plan went through a critic review before any code; the review accepted
five scope decisions with conditions and found two blockers for the Postgres half.

## Decision
- **Two stacked PRs.** M2a is secrets (sources, runner, cache, `setup`, `secret`). M2b is Postgres.
- **D1: verified TLS moves to M3.** Until then, protected secrets go only through sockets and
  exposed ones over plain TCP. A target that sets a TLS field fails validation; it never falls back
  to plain TCP.
- **D2: no fence detection before M4.** With `require_fence = true` (the default), protected
  targets are refused; with `require_fence = false` (a HIGH change in `allow`), results say the
  session is unfenced. M2 is not for real protected secrets.
- **D3: tools take the target as a plain string.** It's looked up in the approved snapshot and its
  kind checked; unknown ids get a fixed error listing the valid ids. A per-kind enum in the schema
  is tech debt.
- **D4: tool paths come from `valetkey setup`**, an interactive, trust-checked command, so `doctor`
  stays read-only ([[valetkey-setup]]).
- **D5: no audit log before M3.** `mcp.log` (agent-readable) never gets statement text or
  parameters.
- **M2b blockers to build in:**
  - role checks cover every role the login role can `SET ROLE` to, not just its memberships
  - memory is bounded by a per-message size cap in the connection wrapper, plus reads through a
    portal limited to `max_rows + 1`

## Why
- Each PR stays reviewable.
- TLS needs its own auth guard and local-address handling.
- Shipping protected-secret use before the fence exists would contradict the fail-closed rule
  ([[2026-10-04-fail-closed-fence-capabilities]]).

## Consequences
- Until M4, valetkey is useful for exposed (`env-file`) targets, and for protected ones only by an
  explicit opt-out.
