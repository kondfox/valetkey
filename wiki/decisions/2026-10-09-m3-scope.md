# M3 ships in two PRs; every write needs approval, and the pre-M4 gap is accepted

Date: 2026-10-09 · Status: Active

## Context
M3 adds the write path (`sql_execute`), out-of-band approval (`valetkey approve`), the audit log
and verified TLS (`docs/design.md §10`). The plan went through three review rounds before any code
(the brief is in [[review]]). Round 1 found nine blockers, round 2 found two, and round 3 approved.
Much of the design detail below comes from those findings.

## Options considered
For the pre-M4 gap, two options were weighed:
1. Refuse `sql_execute` until M4 unless `require_fence = false`, as M2 did for protected targets.
   This was the reviewer's recommendation.
2. Ship it, and record the gap as a residual until M4. **Chosen.**

For audit growth:
1. A per-month cap that stops auditing.
2. Rollover. **Chosen**, because a cap would let the agent stop auditing.

## Decision
- **Two stacked PRs.** M3a covers writes, approval, the audit log and `valetkey log`. M3b covers
  TLS, and its detailed plan is reviewed before its code. The review's TLS findings carry over to
  that plan: SSLRequest strictness, IP-literal hosts, the full local-address set, chain-wide pins,
  CA-bundle trust, ALPN and channel binding. So does the broker's unscrubbed environment
  ([[broker-env-not-scrubbed]]).
- **D1: every write needs approval until M4.** §6.10 skips approval only for targets the agent
  could use without valetkey, and requires it whenever that can't be determined. Determining it
  means reading the sandbox's network rules, which is fence detection (M4). So `confirm_writes`
  isn't added yet.
- **The pre-M4 gap is accepted (maintainer, 2026-10-09).** Approvals are only out of band once the
  fence denies the agent the valetkey root: OS rules for its shell, permission rules for its file
  tools, no unsandboxed retries. M4 generates those rules. Until then the agent could write an
  approval file itself or read pending requests. The maintainer chose not to gate `sql_execute`,
  because the tool won't be used before M4. The gap is recorded in `docs/threat-model.md` (A12c,
  A18 and the residual risks) and in the M4 row of `docs/design.md §10`.
- **D11: the audit and pending dirs become deny-read** (§6.5, enforced from M4). They hold
  statement text and parameters from every project, so leaving them readable would let one
  project's agent read another project's data.
- **The audit records parameters** (§6.7 step 7 didn't list them): an audit of a write without its
  values is incomplete. Every SQL tool caps statements at 64 KiB and parameters at 100 values, 4 KiB
  each and 64 KiB in total, so records stay bounded without truncation.

## Why
The review's findings that shaped the design:
- **Cancellation.** `rmcp` 3.5 doesn't drop a tool handler when the client cancels; it only fires a
  token ([[rmcp]]). A `Drop`-based cleanup would never run, and a late approval would execute a
  write the agent was told had failed. So the wait watches the token, and the shutdown path waits
  for running writes before the runtime is dropped.
- **Partial commits.** Executing a write through a row-limited portal would run a writing `SELECT`
  only partway and then commit that part. It would also never report `rows_affected`. Writes
  therefore execute without a limit and discard the extra result rows.
- **Parsing.** Role-level `standard_conforming_strings`, `DateStyle` or `search_path` change what
  the approved text means. They're pinned at startup, read back, hashed and compared after
  reconnecting.
- **Rendering.** Statement text could imitate the prompt's own lines. It's drawn in a numbered
  gutter, with a broker-built summary next to the prompt.
- **Atomicity.** Concurrent calls could slip past a check-then-insert, so the
  one-request-per-target slot is reserved before the first await. The human may run `allow` during
  the wait, so policy runs again after approval.
- **Audit availability.** A stopping size cap would let the agent switch auditing off by padding
  its calls, so files roll over instead.

## Consequences
- Local dev databases with `.env` passwords prompt on every write until M4.
- `valetkey approve` only works in a normal terminal, and approving a truncated statement needs
  `--full`.
- An `approved` audit record with no outcome record means the outcome is unknown, for example
  after a SIGKILL.
